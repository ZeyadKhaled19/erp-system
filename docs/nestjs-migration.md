# نقل الخادم إلى NestJS

آخر تحديث: 2026-11-21 · اتعمل فوق `main`. كان الأول على فرع `codex/home-ops-dashboard`، واتنقل لـ main لوحده من غير شغل الفرع ده

## الخلاصة

الخادم بقى تطبيق **NestJS 12** واحد (modular monolith) على **Fastify** نفسه، مقسّم لموديولات حسب الشغل. المنطق المحاسبي والمزامنة والتقارير **ما اتغيرش**: الكنترولرز بتنادي نفس الدوال. كل الـ 58 مسار ليهم نفس الطريقة والعنوان والصلاحية وشكل الرد.

`buildApp()` لسه بترجّع Fastify instance، فطرق التشغيل التلاتة ما اتغيرتش: جهاز المحل (`local.ts`)، وبرنامج الويندوز (`desktop.ts`)، وVercel (`vercel.ts`). وده كمان معناه إن كل الاختبارات القديمة بتشتغل على الخادم الجديد من غير أي تعديل.

## المراجعة قبل النقل (Audit)

| البند | الحالة الموجودة |
|---|---|
| الإطار ونقاط الدخول | Fastify 5 في `src/app.ts`. نقاط الدخول: `index.ts`→`local.ts` (جهاز المحل)، و`desktop.ts` (عملية فرعية في Electron)، و`vercel.ts` (serverless)، و`cli.ts` (migrate/backup/restore) |
| قاعدة البيانات | PostgreSQL (`pg`) في الإنتاج، وPGlite محليًا. SQL مباشر عن طريق طبقة `Db` في `db.ts`، من غير ORM. وفيه migrations بـ SQL مضمّنة في `migrations.bundle.ts` |
| حماية البيانات في قاعدة البيانات | triggers بتمنع تعديل القيود وحركات المخزن، وقيد متوازن في آخر كل معاملة (013)، وقيود unique/check/FK |
| الدخول | JWT (HS256، صالح 30 يوم) و scrypt. الجلسة بتتلغي لو كلمة السر اتغيرت. 10 محاولات غلط = إيقاف 15 دقيقة (في الذاكرة) |
| الصلاحيات | صلاحيات الدور + إضافات ومنع لكل مستخدم + نطاق المخازن والخزائن. بتتفحص في المسار وجوه العمليات (`applyOp` والترحيل) |
| تعدد الشركات (tenancy) | **مفيش.** شركة واحدة لكل قاعدة بيانات. فمفيش «عزل شركات» يتنقل أو يتعمل |
| العمل دون اتصال | طابور عمليات بمعرّف `op_id` بيتنفذ مرة واحدة (`processed_ops`)، وتعارضات بتتسجل، وسحب تزايدي بـ `row_version` و `db_epoch` |
| الشغل في الخلفية | النسخ التلقائي كل ساعة (timer في `local.ts`، جهاز المحل والويندوز بس)، وتحديث بداية التجربة كل 5 دقايق (برنامج الويندوز). **مفيش Redis ولا queues ولا cache** |
| منطق في أماكن تانية | migrations وtriggers في قاعدة البيانات، وبرنامج Electron (`desktop/main.cjs`) بيبعت للخادم بيانات الترخيص، والواجهة بتكلم الـ API بس |
| تكاملات خارجية | موقع صاحب السيستم: برنامج الويندوز بيسجل التجربة ويبعت ping. وGitHub Releases للتحديثات ولينك التحميل |
| الاختبارات قبل النقل (main) | shared 15، server 132، web 2، كلهم نجحوا. typecheck نجح. بناء الواجهة نجح. مفيش lint في المشروع |
| مشكلة قديمة (baseline) | `migrations.bundle.ts` كان متولّد من ملف 018 بنهايات سطور CRLF، فاختبار الـ bundle بيفشل في أي checkout نضيف (اللي فيه `.gitattributes eol=lf`). اتصلحت بإعادة التوليد. **مش من النقل** |

## الموديولات

```
apps/server/src
├── app.ts               buildApp(): NestFactory + FastifyAdapter، الواجهة (PWA)، والقفل
├── app.module.ts        CoreModule (DB، الإعدادات، JWT، الحارس العام) + الموديولات
├── core/
│   ├── tokens.ts        رموز الحقن (DB, APP_OPTIONS, JWT)
│   ├── access.ts        الحارس العام AccessGuard، و@Public() و@Perm()، ونطاق المخازن والخزائن
│   └── http.ts          AllExceptionsFilter (نفس شكل الأخطاء)، و404 والـ SPA، وschemaPipe (zod)
├── modules/
│   ├── health/          GET /api/health
│   ├── auth/            الدخول، و/me، وتغيير كلمة السر، ومنع التخمين (LoginThrottle)
│   ├── sync/            push / pull ← applyOp و pull
│   ├── reports/         كل التقارير، وتفاصيل المستند، وبيانات تعديل فاتورة الشراء، وفحص السلامة، ومتوقع الوردية
│   ├── admin/           المستخدمون، والأدوار، وصفحة البداية للدور، والإعدادات، والتدقيق، والأجهزة، والهوية
│   ├── backups/         قائمة النسخ، والإنشاء، والاستعادة، والتنزيل
│   └── licensing/       الترخيص (دايمًا) + مسارات موقع صاحب السيستم (vendor بس)
│
│   المنطق المحاسبي (application/domain) زي ما هو:
├── posting/             الترحيل والمخزون والقيود والسيريال
├── ops.ts               تنفيذ عمليات المزامنة (idempotent)
├── sync.ts, reports.ts, integrity.ts, backup.ts, license.ts, auth.ts, db.ts
```

**القواعد:**
- الكنترولر رفيع: بيقرا الطلب، وبيتحقق منه، وبينادي الخدمة.
- الخدمة: نطاق المستخدم (مخازن وخزائن)، وإخفاء التكلفة والأرباح، والمعاملات.
- المنطق المحاسبي ما بيعرفش NestJS ولا HTTP.
- كل موديول بيصدّر اللي محتاجه غيره بس (مثلًا `LicensingService` علشان القفل).
- مفيش `forwardRef` ومفيش «خدمة عامة لكل حاجة».

## قرارات

| القرار | السبب |
|---|---|
| **NestJS 12 + Fastify adapter** | نفس Fastify اللي كان شغال (5.12.8، ومش متكرر في `node_modules`)، فنفس سلوك JSON والـ headers والـ inject في الاختبارات |
| **حقن صريح `@Inject(TOKEN)` من غير `emitDecoratorMetadata`** | الخادم بيتبني بـ esbuild في كل الأماكن (tsx، وحزمة Vercel، وحزمة الويندوز)، وesbuild ما بيطلعش decorator metadata. الحقن الصريح بيشتغل في التلاتة من غير ما نغيّر طريقة البناء |
| **الحارس العام: كل مسار محتاج دخول إلا `@Public()`** | علشان ما يبقاش فيه مسار مفتوح بالغلط. الترتيب زي قبل: الدخول ثم الصلاحية ثم فحص الـ body |
| **التحقق بـ zod عن طريق `@Body({ schema })` و`StandardSchemaValidationPipe`** | نفس الـ schemas ونفس الرسايل العربي. الخطأ 400 `{ error }` زي قبل. ومسارات الترخيص بتفحص الـ body بعد شرط «ده برنامج الويندوز؟» زي ما كانت |
| **`@HttpCode(200)` على كل POST** | NestJS بيرجّع 201 افتراضيًا، والقديم كان 200 |
| **مسارات موقع صاحب السيستم في موديول ديناميكي** | بتتسجل لما `vendor` بس، فبرّه موقع صاحب السيستم بترجع 404 زي قبل |
| **القفل `onRequest` على Fastify** | لازم يشتغل قبل التوجيه والدخول، وعلى كل `/api` (حتى المسارات اللي مش موجودة) |
| **مفيش BullMQ ولا Redis** | الشغل اللي في الخلفية قليل وبيشتغل كويس بـ timer. Redis معناه برنامج زيادة على كل جهاز عميل (برنامج الويندوز من غير نت)، وVercel serverless ما ينفعش يشغّل worker دايم. ومفيش شغل طويل محتاج يتأجل: التصدير بيرجع على طول، ومفيش إشعارات |
| **مفيش cache** | مفيش مسار قراءة بطيء متقاس. وأي cache للأرصدة أو الصلاحيات خطر على صحة الحسابات |
| **مفيش RabbitMQ** | مفيش خدمات منفصلة ولا تكامل محتاج broker |
| **مفيش تغيير في قاعدة البيانات** | الـ schema والقيود موجودة بالفعل في SQL migrations (أنواع، وFK، وunique، وcheck، وtriggers للقيود). النقل ما احتاجش migration جديدة |
| **@fastify/static 8 ← 10** | ده الإصدار اللي NestJS 12 بيطلبه. `setHeaders` بقت بتاخد reply بدل res، واتعدلت |

## اختلافات معروفة عن السيرفر القديم

اتكتشفوا باختبار العقد (`test/http-contract.test.ts`) وهو شغال على السيرفر القديم والجديد.

1. **cache-control لملفات `/assets`:** القديم كان «ناوي» يبعت `public, max-age=31536000, immutable`، لكن الإضافة كانت بتكتب فوقه `public, max-age=0` (bug قديم، وVercel كان بيبعت immutable من إعداداته). الجديد بيبعت immutable زي ما الكود قاصد، والملفات دي في اسمها بصمة فده آمن.
2. **cache-control لـ index.html على مسارات الواجهة (زي `/pos`):** كان `public, max-age=0` وبقى `no-cache`. الاتنين بيخلّوا المتصفح يتأكد من النسخة كل مرة.

غير كده: نفس الحالات (200/400/401/403/404/409/428/500)، ونفس شكل الأخطاء، ونفس الـ CORS، وتنزيل النسخة المضغوطة، وقائمة المسارات (58 = 58).

## التحقق (اللي اتشغّل فعلًا)

| الفحص | النتيجة |
|---|---|
| `npm run typecheck` (shared + server + web) | نجح |
| `npm test` | shared 15 ✓، server 143 ✓ (القديمة 132 + 11 اختبار العقد)، web 2 ✓ |
| اختبار العقد على **سيرفر main القديم** (`CONTRACT_APP=<المسار>/app.ts`) | 11/11 (مع الاختلافين المكتوبين فوق) |
| مقارنة جدول المسارات القديم والجديد (وضع vendor) | 58 = 58، ومفيش فرق |
| `npm run build` (الواجهة) | نجح |
| `node scripts/build-vercel.mjs` | نجح (حزمة 3.7MB) |
| تشغيل حزمة Vercel على PostgreSQL حقيقي (pglite-server، بيانات مؤقتة) | health `db: postgres`، والدخول، وpush، وpull، ومسار vendor، والتنزيل: كلهم 200 |
| حزمة الويندوز (نفس bundling بتاع `prepare.mjs`) كعملية فرعية زي Electron، على المنفذ 4100 ببيانات مؤقتة | health، والدخول، وpull، وتقرير، و401، وصفحة الواجهة: كلهم مظبوطين |

**ما اتجربش:**
- النشر الفعلي على Vercel. محتاج push، وده قرارك.
- ملف تسطيب الويندوز الكامل (`npm run desktop:dist`)، لأن مكتبات Electron مش متسطبة في الـ worktree. bundling الخادم اتجرب بنفس الإعدادات.
- الواجهة كاملة في المتصفح على الخادم الجديد. اتجرب `/pos` والـ API بس.

## الرجوع (Rollback)

النقل كله في commit واحد على main، ومفيش تغيير في قاعدة البيانات، فالرجوع = تشغيل الكود من الفرع القديم. البيانات بتشتغل مع الاتنين.

## حاجات ممكن تتعمل بعدين (مش ضرورية للنقل)

- نقل ملفات المنطق (`posting/`، `ops.ts`، `reports.ts`…) جوه موديولاتها. ده نقل ملفات بس من غير تغيير سلوك.
- فحص متغيرات البيئة بـ schema عند التشغيل، ولوجات منظمة بـ correlation id. ما اتعملوش علشان ما يغيّروش سلوك التشغيل الحالي على أجهزة العملاء.
